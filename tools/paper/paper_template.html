Zero-Trust SDN at the Edge

Continuous behavioural verification of edge servers, enforced as OpenFlow rules — and why a trust score alone provably cannot do it.

System: Zero-Trust-Enabled SDN Architecture Platform: os-ken · OpenFlow 1.3 · Mininet Report compiled: 16 August 2026 Test suite: 669/669 passing

Abstract

Edge and multi-access edge computing distribute workloads across many small, physically exposed, heterogeneously-owned servers. Classical load balancers — round-robin, least-connections — schedule on what those servers claim about themselves, an assumption no compromised node respects. Zero Trust prescribes continuous verification as policy, but leaves open how a network control plane verifies serving infrastructure and acts on the verdict in the data path.

We present and evaluate a trust-aware SDN load balancer that computes a per-node trust score from observed task outcomes and telemetry, ranks edge servers by a composite EdgeScore, and enforces exclusion as real OpenFlow drop rules. Our central result is negative and, we argue, generalisable: the widely-published EMA trust formula cannot isolate a node that lies about its load while still serving tasks correctly. We derive the arithmetic floor (T = 0.44 against an isolation threshold of 0.30), confirm it against the shipped implementation, and confirm it live — in a 215-second emulation, the Sybil attacker's trust never fell below 0.312 and it was caught only by an independent anomaly gate, while the blackhole attacker was caught only by the trust score and never raised an anomaly at all. Neither detection rail alone catches all four server-side attacks; both are necessary.

Across three complementary evaluations — a live Mininet run (8 edge servers, 40 IoT devices, 6 attack classes), 600 seeded paired simulations against four baselines, and a queueing sweep to N = 64 — the system detects 8/8 attacks, classifies 95.8% of 48 subjects correctly, never wrongly labels an honest node, keeps honest-node availability at 100%, and reduces SLO violations by 19.7–68.8% against incumbent load balancers and by 15.1–29.8% against its own trust-ablated twin (paired Wilcoxon, Holm–Bonferroni, padj = 6.9×10⁻⁶, r = +1.00).

An online UCB1 bandit that learns the routing weights is reported as a negative result: across the run the candidate weightings are statistically indistinguishable, and we identify the cold-start artifact that would otherwise have been read as the learner beating the hand-tuned default.

Trust decisions are recorded in a Merkle-committed, hash-linked ledger costing 0.130% of task latency, whose tamper evidence localises a single-digit edit to the two blocks at the seam rather than merely invalidating the chain — a resolution that depends on recomputing predecessor digests, since under the conventional stored-hash comparison the same edit passes every link check undetected. We also report where the system loses: with no attacker present it is 4.8–10.7% worse than round-robin, a cost we trace to load-signal staleness rather than to trust, and at N = 4 the capacity removed by quarantine costs more than the attack.

1Introduction

Edge computing pushes computation onto gateways, roadside units, factory-floor servers and campus racks. Three facts collide there. The perimeter model fails, because a node inside the network can be compromised, rented, misconfigured or simply selfish. Self-reported telemetry is the industry norm and is trivially gameable — Kubernetes metrics, cloud auto-scalers and MEC orchestrators all schedule on what a node says about itself, so a node that under-reports load attracts traffic. And Zero Trust [1] is an architecture document: it says "never trust, always verify, continuously", but says little about how a control plane continuously verifies the serving infrastructure and acts on the result in the data path.

The question this work answers is therefore narrow and concrete:

Research question

Can an SDN control plane continuously verify edge servers using observed rather than claimed behaviour, and enforce the verdict in the data plane fast enough to matter?

We answer it affirmatively at prototype scale, with an important qualification that turned out to be the most transferable part of the work. The trust formula the project set out to implement — a weighted EMA over reputation, behaviour, honesty and anomaly terms, of the family that recurs throughout the trust-aware routing literature — is insufficient by construction. Its anomaly term can only ever subtract a bounded amount, so a node that lies about its load while still completing every task correctly settles at a trust value comfortably above any isolation threshold that honest nodes must also clear. We did not patch the formula. We characterised the gap, added an explicit second detection rail, and measured both.

1.1Contributions

  1. A characterised insufficiency result for score-based trust. We derive the trust floor for a non-degrading liar analytically, verify it against the shipped calculator, and demonstrate it in a live run where the Sybil attacker is caught exclusively by the anomaly gate (§7.1).
  2. Evidence that the two rails are complementary, not redundant. Of four server-side attackers in one live run, two are caught only by the anomaly gate, one only by the trust score, and one by both — with the gate firing 84 s earlier (§7.1).
  3. Data-plane enforcement with measured bounds. Trust verdicts become OpenFlow drop rules and VIP rewrites, with routing decisions at 2.02 ms mean and quarantine re-dispatch at 51.29 ms mean (§7.3).
  4. A statistically-grounded comparison against four baselines including a trust-ablated variant of the same selector, over 600 paired seeded runs with Holm–Bonferroni correction and reported effect sizes — including the two comparisons the system loses (§7.4).
  5. A tamper-evidence result with forensic resolution. We show the hash-linked trust ledger localises an edit to the seam — the edited block and its successor — rather than merely reporting the chain as broken, and that this depends on recomputing predecessor digests rather than trusting stored ones, a distinction under which a realistic tamper goes entirely undetected (§7.6).
  6. A measured negative result on learning the routing weights. An online UCB1 bandit over five weight presets could not separate them: the four arms with clean measurements span 0.0166 of reward. We also identify the cold-start artifact that would have made the hand-tuned default look 0.5 reward worse than it is (§7.7).
  7. A separation result for selection strategy under scale showing that argmax selection, not hardware, is what stops the fleet scaling, and that the two metrics an evaluation would most naturally report — throughput and delivery ratio — fail to separate the strategies in the regime the deployment actually occupies (§7.5).

2Background and related work

2.1Zero Trust and continuous verification

NIST SP 800-207 [1] frames Zero Trust around per-request access decisions informed by continuously-updated signals. Commercial implementations overwhelmingly verify users and client devices at access time. Verifying the serving infrastructure itself, continuously, with routing consequences, is considerably less settled — and is the gap this system occupies.

2.2Trust models for distributed and edge systems

Reputation systems for peer-to-peer and WSN settings established the weighted-component, EMA-smoothed trust score as a standard device. The formula evaluated here, T = αR̄ + βB̄ + γH̄ − δĀ, is representative of that family. Our insufficiency result (§7.1) is a property of the bounded-subtraction structure shared across the family, not of one parameterisation, which is why we report it as a finding rather than a tuning note.

2.3Load balancing under stale and adversarial information

Mitzenmacher's power-of-two-choices [2] and the stale-information analyses of Mitzenmacher [3] and Dahlin [4] supply both the fix we adopt for starvation and the explanation for the one place our system loses. Least-connections on a stale signal herds — every arrival within a polling window sees the same snapshot and piles onto whichever node last looked idle. This is why our strongest classical baseline is also, in practice, the weakest strategy measured.

2.4Lightweight cryptography and tamper-evident records

PRESENT-80 [5] is an ultra-lightweight block cipher designed for constrained devices; we use it as the primitive behind challenge–response device admission. Merkle trees [6] and RAFT [7] supply tamper-evidence and replication for the trust-record ledger.

We use "blockchain" in its narrow, defensible sense and it is worth drawing the boundary early, because the word invites claims this system does not make. What is present is an append-only, hash-linked, Merkle-committed record with reproducible verification by a party other than the writer. What is absent is a permissionless network, any consensus over mutually distrusting writers, proof-of-work or stake, and Byzantine fault tolerance. The ledger detects modification after the fact; it does not prevent it, and it does not survive a malicious controller. §4.5 describes the construction and §7.6 measures both its cost and the precision of its tamper evidence.

2.5Trust-aware SDN and edge systems

Recent work combines several of these ingredients directly. Ali et al. [11] pair a blockchain record with a zero-trust capability framework for MEC task load balancing; TREN [12] applies SDN and zero-trust architecture to smart-city edge networks under DDoS and Sybil attack; and Huang et al. [13] propose a two-tier trust evaluation for service-oriented edge–cloud networks. We defer detailed positioning to §8.3, where the comparison can be made alongside our own results — and where we explain why the numeric comparison across these systems is weaker evidence than it appears.

3Threat model

The controller is trusted. This is a real limitation and we state it plainly: the control plane is a single point of both failure and trust, and nothing here evaluates a malicious controller. The ledger's replication model is crash-fault, not Byzantine.

Edge servers and IoT clients are untrusted. Adversaries are non-adaptive: each attacker follows a fixed behavioural program and does not observe or react to its own detection. Attacks arm on a delayed onset, so every attack has a clean baseline interval before it and an attacker is behaviourally identical to an honest node until it arms.

Two modelling decisions are load-bearing. First, the flood tell is keyed on the requesting client, never on the edge server it lands on — a server drowning under a flood is not lying about its load, it is telling the truth about being overwhelmed, and blaming it would manufacture a false positive on an honest node. Second, a node that stops answering health checks is scored as node_down, never folded into blackhole: this system's blackhole answers health checks perfectly and drops only work, so silence is a liveness failure. Folding it in would inflate exactly the detection numbers the evaluation exists to measure honestly.

4System architecture

The product is the controller application, its REST API and the live dashboard; it runs against any OpenFlow 1.3 switch. Mininet, the node agents and the IoT clients are the test harness, not the system under test.

4.1The trust score

Each completed or failed task produces a trust update. Four components are smoothed by an exponential moving average and combined:

T(t) = α·R̄(t) + β·B̄(t) + γ·H̄(t) − δ·Ā(t) α=0.35 β=0.25 γ=0.25 δ=0.15 X̄(t) = λ·X(t) + (1−λ)·X̄(t−1) λ=0.85 R reputation success 1.0 / timeout 0.3 / failure 0.0 B behaviour max(0, 1 − latency_ms / 500) H resource honesty max(0, 1 − |claimed − observed| / 0.5) A anomaly 1.0 when the monitor flagged the node this cycle

4.2The routing decision

Eligible nodes are ranked by a composite score; quarantine is applied before ranking, never as a score penalty, so no weighting can ever return a quarantined node to service.

EdgeScore(n) = w₁·T(n) + w₂·(1 − cpu_load(n)) + w₃·(1 − lat_norm(n)) 0.50 / 0.30 / 0.20 eligible(n) ⟺ T(n) ≥ 0.30 ∧ Ā(n) < 0.50 the two rails n* = best of d=2 uniformly sampled eligible nodes p2c, ε=0.05 exploration

Note that cpu_load is the node's claimed load. This is deliberate: the lie is what makes a Sybil attractive to the balancer, and modelling it as observed would define the attack away.

Selection is power-of-two-choices with ε-exploration rather than argmax. Under argmax, once trust — the heaviest term — entrenches roughly two nodes, the rest starve regardless of fleet size. p2c breaks the lock-in; ε-exploration closes the residual gap that p2c leaves, since the strict-worst node under frozen scores is never the better of any sampled pair. §7.5 quantifies both.

4.3The second rail: the anomaly gate

An independent monitor evaluates two pure-function tells per cycle — a latency tell (a node claiming idle while answering health checks slowly, relative to the fleet median) and a timeout-rate tell — and produces a smoothed anomaly level Ā. Reaching Ā ≥ 0.50 quarantines the node regardless of its trust score. §7.1 is the argument for why this gate is necessary rather than belt-and-braces.

Two disciplines apply to both rails. A detector with no recent evidence abstains rather than re-asserting its last verdict — without this, quarantine is an absorbing state, because quarantine cuts the service traffic that produces the only outcomes the score is built from. Nodes quarantined on trust alone, with the anomaly rail clear, are offered one probe task every 5 s so they can earn trust back. Both rules were derived from a live run that ended with three provably healthy nodes permanently isolated.

4.4Enforcement, admission and record-keeping

Decisions become flow rules: a VIP rewrite installs the chosen server into the data path; quarantine installs a drop rule at a reserved priority and tears down the offending node's existing flows. Between full service and quarantine sits a rate-limited band enforced by OpenFlow meters, so a merely-suspect node is metered rather than either trusted fully or cut off.

Device admission runs a five-step PRESENT-80 challenge–response with a 30 s nonce TTL, extended with a provisioned source-IP pin. The pin is the part that matters: because the key is fleet-wide, the cipher authenticates possession of the key, not the device.

4.5The trust ledger

Every quarantine in this system is an accusation, and an accusation that cannot be audited afterwards is difficult to operate against and impossible to appeal. The ledger exists to make the trust record reconstructible and tamper-evident: given the chain, an auditor can establish what the controller believed about each node, when, and on what evidence — and can detect after the fact if any of it was edited.

Structure

Trust updates are batched and committed as blocks. Each block carries a Merkle root over its batch and a SHA-256 digest over its own header, which includes the previous block's digest:

leaf(u) = SHA256(canonical_json(u)) one trust update node(l, r) = SHA256(l ‖ r) positional, NOT sorted merkle_root = fold node() over the leaf layer odd layer duplicates its last header = {index, timestamp, previous_hash, merkle_root, proposer_id, raft_term} block.hash = SHA256(canonical_json(header)) sorted keys

Two structural choices carry weight. Sibling concatenation is positional and deliberately not sorted. A Merkle proof records whether each sibling sits left or right of the running hash, and verification replays that order; sorting the pair would make the tree order-agnostic and silently weaken every proof it issues. raft_term is inside the hash preimage from the start, even though the live path pins it to 0 — so a consensus backend can populate the term later without changing how any block hashes.

Genesis is pinned to timestamp = 0.0 rather than wall-clock time. This looks like a detail and is not: each replica in a RAFT cluster constructs its own ledger independently, so a wall-clock genesis would give every replica a different anchor digest and every subsequent block would mismatch on previous_hash despite identical content. A single-replica deployment never notices, because it only ever compares its chain against itself.

Independent verification, and why it is not the controller's job

The controller exposes a chain-validity endpoint, but a dashboard that renders that flag is the controller auditing its own ledger with the code that wrote it — a verdict that can never contradict the thing it is checking, and a tamper demonstration driven by it would be theatre. The block header is therefore streamed to the browser, which recomputes the SHA-256 itself from the preimage and displays both verdicts side by side without merging them. The page rebuilds the genesis block from the pinned constants too, so the chain's anchor is not taken on faith either.

One consequence is worth stating because it is stricter than the conventional check. The browser's link check compares each block's previous_hash against the recomputed digest of its predecessor, not the predecessor's stored hash field. Against a block whose contents were edited without recomputing its stored digest, the stored-hash comparison still passes and the damage never propagates, so the chain reads as "one bad block" rather than as broken linkage. §7.6 measures the difference.

Replication

A transport-agnostic RAFT core [7] implements leader election and log replication behind the same commit interface the controller already uses, with a TCP transport carrying length-prefixed JSON — not pickle, since these sockets face the network and pickle deserialises arbitrary code, which is an indefensible attack surface in a system whose thesis is zero trust. This is built and unit-tested but is not wired into the running controller, whose live path remains a single local replica. We report its timings as standalone measurements and make no consensus claim about the live figures (§9).

4.6Learning the EdgeScore weights

The weights w₁/w₂/w₃ are hand-picked constants, which raises an obvious question: are they the right ones? A UCB1 multi-armed bandit answers it online. Each arm is a complete, validated EdgeWeights triple; every 10 s window the controller observes what happened under the active arm, scores it, and picks the next:

reward = success_rate − λ·mean_normalised_latency − μ·load_imbalance λ = μ = 0.2 select = argmax over arms of ( mean_reward(a) + c·√( ln N / n(a) ) ) c = 1.41

The latency term is not decoration. Without it the reward is flat whenever the fleet is healthy enough that everything succeeds regardless of weighting, and the bandit has no gradient to learn from; it is what distinguishes arms in the common, non-degraded case. The imbalance term (standard deviation of per-node load) rewards spreading work rather than piling it on one node.

The optimiser can only ever rewrite w₁/w₂/w₃. The quarantine gates are outside its reach by construction, because exclusion happens before scoring (§4.2) — so no reward signal, and no amount of learning, can weight a malicious node back into eligibility. This is the safety property that makes an online learner acceptable in a security control loop at all.

5.1Pairing and statistics

Every strategy runs on the same 30 seeds, and each simulated quantity draws from its own RNG stream — common random numbers. With a single shared stream the draws interleave differently once strategies diverge, and the pairing silently decays into independent sampling.

We use the paired Wilcoxon signed-rank test, not a paired t-test: the outcomes are rates bounded in [0,1], visibly skewed and zero-inflated, so normality would be doing real work in the result. Four baselines is a family of four tests per scenario, so every p-value is corrected with Holm–Bonferroni within its scenario; both raw and adjusted values are reported. Because a p-value says a difference exists rather than that it matters, each comparison also reports the matched-pairs rank-biserial correlation r and the median difference in the metric's own units.

One deviation, reported rather than absorbed. The installed SciPy (1.8.0) does not tabulate the exact signed-rank null at n = 30, so those comparisons fall back to the tie-corrected normal approximation. This is the conservative direction — the approximation yields the larger p-value — but it is a different test from the one requested, so the reporting layer now records and prints which null each comparison actually used.

5.2The primary metric

A task violates the SLO if it never completed or completed slower than 500 ms. We make this the primary metric rather than latency because latency flatters black holes: latency is only defined for tasks that finished, so a strategy feeding 11.5% of its traffic into a node that never responds has its worst outcomes excluded from its own latency distribution. In the drop scenario, raw p95 latency appears to favour random (601 ms) over the full system (637 ms) — while random fails 445 tasks and the system fails 7. Any latency comparison across strategies with materially different failure rates is survivorship-biased.

7Results

7.1Score-based trust cannot isolate a competent liar

Consider a node that under-reports its load but still completes every task correctly and quickly — the pathological Sybil. Its reputation term saturates at R̄ → 1.0 because it never fails a task. Its behaviour term is near-maximal because it answers fast. Only the honesty term collapses to H̄ → 0, and only the anomaly term is subtracted — and it is subtracted with a weight of δ = 0.15. The floor is therefore:

T = 0.35(1.00) + 0.25(0.96) + 0.25(0.00) − 0.15(1.00) = 0.44 isolation threshold = 0.30

Driving the shipped TrustCalculator — not a mock — to steady state confirms it exactly:

Table 4. Steady-state trust from the real calculator over 400 updates. The competent liar sits 0.14 above the isolation threshold; only the node that actually fails tasks crosses it.

The structure of the result matters more than the constants. δ can only ever subtract δ. Any formula of this family in which dishonesty enters only as a bounded negative term has a liar floor, and that floor sits above any isolation threshold low enough that honest nodes under transient load do not trip it. Raising δ far enough to catch the liar would make the threshold unsurvivable for honest nodes; the parameters trade off against each other and there is no setting that separates the two. This is why we added a gate rather than retuning.

Principal finding

Two of the four server-side attackers were quarantined only because of the anomaly gate — their trust never crossed the isolation line. One was quarantined only because of the trust score — it never raised an anomaly signal at all, because a blackhole answers health checks at full speed and lies about nothing. The fourth was caught by both, with the gate firing 84.3 s before the score.

Removing either rail would have let attacks through. Continuous verification in this setting is not a scoring problem; it is a problem of running independent detectors on independent evidence and combining them disjunctively.

  • srv3 sybil → on-off. Naming on-off requires observing a quiet stretch. srv3 was quarantined 8 times, and each quarantine produces a genuinely quiet stretch that is indistinguishable from an attacker's off phase.
  • srv6 blackhole → grayhole. Blackhole and grayhole fire the same signal and differ only in magnitude. srv6 was isolated at +13.6 s and spent 79.7% of the run isolated, so the drop tell never accumulated enough samples to measure a rate, and the family verdict came from the trust rail — which cannot claim magnitude.

A tension worth naming

Containment quality and magnitude evidence are in direct opposition. The faster an attacker is isolated, the less evidence exists to establish how much it was misbehaving. Both classification misses in this run are consequences of the defence working well, not badly. An evaluation that optimised the confusion matrix would be selecting for slower containment.

The third row is the identity spoof. The controller's own denial text reads: "iot1 is provisioned to 10.0.0.1, request came from 10.0.0.38 (identity spoofing — correct key, wrong host)". Because the fleet shares one key, PRESENT-80 alone would have admitted this device — it presented a perfectly valid response. Only the provisioned source-IP pin refuses it, and only the structured denial kind lets the classifier tell this apart from iot39/iot40, who simply never had the key.

Two design consequences worth stating. The denial is keyed on the source IP, not the claimed identity — an earlier version blamed the victim, since the claimed device_id is the attacker's choice and the honest owner of that name is the one who gets punished for it. And the client never retries a 403, only transport failures: retrying a genuine refusal would turn every wrong-key device into an authentication flood.

Escaping quarantine

Quarantine cuts the service traffic that produces the only outcomes the trust score is built from, so without a deliberate escape route it is an absorbing state: a node below the isolation threshold can never climb back over it. An earlier run of this system ended with three provably healthy nodes — anomaly 0.0, 29 ms round-trip, zero in-flight — permanently isolated at trust ≈ 0.18.

The escape route is a probation probe: a node quarantined on trust alone, with its anomaly rail already clear, is offered one trial task every 5 s. The anomaly gate is never relaxed this way, so a node the second rail has flagged is never probed, and the exposure is bounded at one task per node per interval. In this run it produced 19 recoveries against 22 quarantines, and no honest node finished the run isolated.

One mechanism deserves specific mention because it fired 21 times (0.52% of 4,013 reports). When quarantine tears down a node's flows, in-flight client connections die on a dead socket while the dispatch record has already moved to a survivor. The client times out and reports a failure — but the receiving node was never asked. Charging that timeout to the survivor is a wrong-node attribution, and it previously caused an honest node to be mislabelled as a grayhole and quarantined twice. Re-steered dispatches are now marked non-chargeable structurally, with no tuned threshold, and the report is still published (so availability and delivery ratio keep counting the client's real loss) with an explicit charged: false flag so the abstention is re-derivable offline.

Everything that reads the signal improves monotonically as the signal freshens, and by 0.01 s the full system is the best strategy on the board. The same effect explains why least_conn — the strongest classical baseline in theory — is the weakest strategy measured: this is precisely Mitzenmacher's herd behaviour [3] and Dahlin's "stale least-loaded performs worse than random" [4].

The capacity cliff

Isolating a node removes its capacity. When attackers are a large fraction of a small fleet, the survivors absorb everything and the resulting queueing can cost more than the attack did. At N = 4 with 2 attackers, the system loses the headline metric (0.4377 vs 0.3505) while still beating the ablation on every component — 17× fewer failures, 22% lower p95. By N = 6 the cliff is gone. The defence needs enough spare capacity to absorb what it isolates, and that is a deployment constraint, not a tuning parameter.

7.5How the selection rule scales

The live testbed is a 4-core host; running N = 64 live would measure the laptop, not the architecture. We therefore sweep fleet size in a queueing model (M/M/c per node, unbounded FIFO, real task timeouts) that drives the real selector. A timed-out task is counted as loss but deliberately not removed from the node — the client abandoned it, the node has no idea, the worker stays occupied — and that wasted capacity is what makes an overloaded fleet degrade rather than gracefully shed load.

p2c scales linearly; argmax saturates at ~85 tasks/s from N = 8 and never improves again. Its delivery ratio collapses from 99.2% to 10.5% with delay pinned at the timeout ceiling. Three observations:

  • argmax fails in two different ways at the two ends of offered load, which is why load became a sweep axis rather than a fixed setting. At 10% load it starves: 13 of 16 nodes idle, Jain fairness 0.176. At 60% almost nothing is starved (Jain 0.75–0.94) because queues finally push the CPU term away from the favoured nodes — the fleet ends up balanced and broken. Reporting either end alone makes argmax look merely unfair, or merely slow, instead of both.
  • p2c is not a per-decision CPU win, which is worth saying because it is the intuitive claim and it is wrong here. Both strategies cost the same and both grow roughly linearly with N (3.6 → 38 µs from N=4 to N=64), because the selector scores and sorts every eligible node regardless of strategy — that ranking is returned as the explanation of the decision. Explicability bought with CPU that is nowhere near a bottleneck.
  • In the deployed configuration's own regime, throughput and delivery ratio do not separate the strategies at all. Sweeping client count from 20 to 40 against the shipped 8-server roster, p2c and argmax are within 3% on both — while argmax runs the entire workload on 3 of 8 machines (Jain 0.281 vs 0.936) and pays for it in a mean delay that climbs 300 → 670 ms where p2c's stays flat at 196 → 204 ms. An evaluation reporting only throughput and PDR would conclude the selectors are equivalent.

7.6Ledger integrity and cost

The ledger makes two claims — that it is cheap, and that it is tamper-evident. Both are measurable, and the second is measurable in a more useful way than "the chain went red".

Cost

Across the live run the controller committed 399 blocks at exactly 10 updates per block, at a mean commit cost of 1.679 ms (median 1.494 ms, p95 2.980 ms, max 7.944 ms). Total time spent inside commit() across the entire 215.1 s run was 670 ms, which amortises to 0.168 ms per trust update against a 128.7 ms mean end-to-end task latency — an overhead of 0.130% against a 15% budget.

Tamper evidence

We built a 21-block chain (genesis plus 20 commits of 10 updates), confirmed it validates, then flipped a single hex digit of block 10's Merkle root — the field that commits to the batch of trust records, so editing it is precisely what "somebody rewrote a trust decision" looks like.

The useful part of this result is the shape, not the pass/fail. The edited block fails its own digest and its immediate successor fails its link; every block to the right still verifies, because each chains correctly to an untouched predecessor. The chain does not merely report that something is wrong — it reports where, which is the forensically actionable outcome.

Why the link check must recompute

We repeated the experiment editing a block's contents without updating its stored hash field — the natural move for an adversary with write access to the record store. Comparing each block's previous_hash against the predecessor's stored hash, every link passes; the tamper is invisible to the linkage check. Comparing against the recomputed predecessor digest catches it immediately.

Recomputation is therefore not an implementation detail — it is what separates a chain that is genuinely tamper-evident from one that is merely internally consistent with its own stored checksums.

Inclusion proofs

A Merkle root over a 10-record batch admits inclusion proofs of 4 sibling hashes. A record that is in the batch verifies against the root; a record that is not is rejected; and swapping two leaves changes the root, confirming the positional-concatenation property the proof format depends on. This is the mechanism by which a single trust decision can be proved to belong to the committed record without disclosing or re-transmitting the rest of the batch.

7.7Does learning the weights beat hand-tuning?

The honest answer from this run is no, and it cannot tell — which is a more useful result than a claimed improvement would have been.

Over 20 windows the bandit pulled all five arms and the rewards came out almost indistinguishable. Excluding the one arm affected by the artifact below, the four remaining arms span a total of 0.0166 of reward:

A trap worth reporting

Read naively, Table 17 says the hand-tuned default is by far the worst arm — 0.3546 against ~0.86 for everything else. That reading is wrong, and the way it is wrong is instructive.

The default arm was active for exactly two windows. The first was the run's opening window, in which zero tasks completed: no task had finished yet, so success_rate was undefined-by-absence and the window scored −0.2122. Its other window scored 0.9213 — the highest single-window reward recorded in the entire run. Averaging a measurement of nothing together with the best measurement taken produces a number that describes neither.

An optimiser that ran long enough would wash this out. One evaluated over 20 windows does not, and a paper reporting "the learned weights beat the hand-tuned default by 0.5 reward" from this table would be reporting a cold-start artifact as a finding.

Three things follow, and we state them as limits rather than results:

  • The arms are too close to separate at this horizon. UCB1 keeps exploring — 5/5/5/4/1 pulls — precisely because the confidence intervals never stop overlapping. That is the algorithm behaving correctly on a problem with no clear winner, not a failure to converge.
  • The workload is too easy for the reward to discriminate. At 12% host utilisation nearly every task succeeds under every weighting, so the success_rate term — the dominant one — is close to saturated, and the two penalty terms are left to carry a signal they were designed to supplement rather than replace.
  • A reward window with no outcomes should abstain, not score. This is the same discipline the detectors already follow (§4.3) and the optimiser does not yet implement it. It is a one-line change and we flag it as such rather than quietly excluding the window from the table.

What the run does establish is that the optimiser is safe and live: it ran for the whole run, rewrote the weights 20 times, never touched the quarantine gates, and produced no measurable harm — mean reward over the second half of the run (0.8876) was higher than over the first (0.7438), though that comparison is itself confounded by the cold-start window and by attackers arming partway through.

8Discussion

8.1A Sybil lie is self-defeating when telemetry is real

Because the node agents perform real bounded work rather than emitting synthetic telemetry, a liar advertising "I'm idle" attracts traffic it cannot serve, genuinely degrades, times out, and collapses its own trust. This emergent self-punishment exists only because the testbed measures real load — most simulation studies in this space inject telemetry, and would not observe it. The pathological case, a liar with enough spare capacity that it never degrades, is precisely the case the anomaly gate covers. The two results compose into one story: where the lie costs the liar, trust suffices; where it does not, only an independent detector does.

8.2Honest packet visualisation in SDN is structurally hard

Once a flow rule is installed, matching packets are forwarded entirely in the data plane and never reach the controller again. A controller therefore cannot honestly animate per-packet flow from packet-in events. The dashboard drives its animation from 1 Hz flow-statistics counter deltas and prints the measured packet rate on screen so the claim is checkable. This is a small but real constraint on SDN observability, and it is the honest answer to "why doesn't your dashboard show every packet?"

8.3Positioning against prior work

Several recent systems combine trust evaluation, SDN and edge computing, and it is fair to ask what this one adds. We answer that in two parts, because the two available kinds of comparison have very different evidential weight.

What can be compared numerically, and what cannot

Cross-paper performance numbers in this area are not comparable, and we do not present them as though they were. The systems below run different workloads, topologies, attacker populations and class balances, and — decisively — different definitions of the headline metric. An "accuracy" computed over a two-class DDoS/Sybil problem and one computed over an eight-class problem with 40 honest subjects are not the same quantity. The table that follows records what each system reports under its own conditions, as context for where this work sits, and not as a controlled ranking.

What this work adds that the comparison table cannot show

The systems in Table 18 report how well a trust mechanism performs. None of them reports a limit of the trust mechanism itself, and that is this paper's distinctive contribution. Three differences follow from it:

  • A structural insufficiency result rather than an accuracy figure. We show that the EMA trust-score family has an arithmetic floor against a competent liar, that the floor sits above any survivable isolation threshold, and — in the live run — that two of four attackers are caught only by the independent gate while a third is caught only by the score (§7.1). A system reporting 95% detection from a single trust rail cannot tell whether its remaining 5% is noise or is this structural blind spot.
  • Enforcement in the data plane, timed. Trust verdicts here become OpenFlow drop rules with a measured 51.29 ms mean re-dispatch, rather than remaining policy decisions inside the controller. That is a different claim from "the framework decides to deny access".
  • Reported losses. We report the two comparisons the system loses, the regime where quarantine costs more than the attack (N = 4), the survivorship bias that makes latency flatter black holes, and the tension by which faster containment degrades classification precision. A comparison table of headline numbers systematically hides exactly this class of finding — in every paper, including this one.

8.4Methodological observations

Three of these cost us real defects before they became rules, and we think they generalise:

  • A replay measures only first-order effects. When a suspected defect sits inside a feedback loop, replaying a fixed recording gives a lower bound and only a re-run settles it. We predicted a fix would not restore availability on its own, based on a static replay showing anomaly cycles dropping only 212 → 174; the false positives we read as an independent problem were downstream of the same cascade, and removing the first link took honest availability from 48.05% to 98.90%.
  • Separate "correctly isolated attacker" from "wrongly quarantined honest node" in every metric that touches quarantine. Averaging them hides whichever one matters.
  • A flat line in a chart is a hypothesis about the data before it is one about the chart. Three recording-fidelity defects surfaced from looking at a flat series — including one that had been causing an offline report to read zero throughput for months. The charts did not introduce the fault; they made an existing one visible.

9Limitations

Stated in full, because several bound the claims above directly.

  1. The controller is a trusted single point. Nothing here evaluates a malicious or compromised controller, and in a federated deployment "who runs the controller?" becomes the dominant trust question.
  2. Crash-fault, not Byzantine. The ledger is tamper-evident, not tamper-proof, and detects modification rather than preventing it. RAFT tolerates replica crashes, not lying replicas.
  3. RAFT is built and unit-tested but not integrated. The live path is a single-replica local ledger. Consensus timings are measured standalone and are reported as such; no consensus is running behind the live figures.
  4. Single live run, single seed. Every live figure comes from one 215 s run. No confidence intervals. Statistical claims come exclusively from the 600-run paired harness, and the two must not be conflated.
  5. The live run was 215 s against a configured 300 s, which costs the on-off attacker roughly four periods of evidence and is the likely reason its detection latency (36.3 s) is the run's worst.
  6. Attackers are non-adaptive. An adversary that observed its own quarantine and modulated its response time would defeat the latency tell. The claims are bounded to the seven classes in Table 1.
  7. Scale beyond 8 nodes is simulation. The sweep drives the real selector, but it is not a live run. It supports "the selection rule, not the hardware, is what stops scaling"; it does not support a capacity figure for 40 real machines.
  8. DDoS response is detection-only. Flooding is detected and classified but not throttled — that needs a per-client-IP flow path, where today's rate-limiting is per-edge-node. Deferred as real scope rather than half-built.
  9. PRESENT-80 is a reference implementation. It is not constant-time, makes no side-channel guarantees, and an 80-bit key is below modern recommendations regardless. The contribution is the architecture — challenge–response admission behind a swappable authenticator seam, with source-IP pinning closing the fleet-key gap — not the cipher.
  10. The weight optimiser is unevaluated rather than evaluated-negative. Twenty windows at 12% host utilisation cannot separate five weightings whose rewards differ by 0.0166, and its reward window scores rather than abstains when no task completed. Nothing here shows learned weights are no better than hand-tuned ones — only that this experiment could not tell.
  11. One workload shape. Poisson arrivals at 40% of farm capacity. Bursty and heavy-tailed workloads are untested.

10Conclusion

An SDN control plane can continuously verify edge servers from observed behaviour and enforce the verdict in the data plane within tens of milliseconds. Across a live emulation and 600 seeded comparisons the system detects every attack it is shown, never wrongly accuses an honest node, holds honest-node availability at 100%, and reduces SLO violations by 15–30% against an otherwise-identical trust-blind selector and by up to 69% against classical baselines.

The result we would most want carried forward is the negative one. A weighted trust score of the standard EMA family cannot isolate a node that lies about its state while still doing its work, because dishonesty enters only as a bounded subtraction and the floor it leaves sits above any threshold honest nodes can survive. We measured that floor, confirmed it in a live run where the Sybil attacker's trust never fell below 0.312, and found the converse case in the same run — a blackhole attacker that raised no anomaly signal whatsoever and was caught by the score alone. Neither rail is sufficient; both are necessary; and a design that reports only one of them will be confidently blind to half its threat model.

The supporting record deserves one sentence of its own, because "blockchain" is usually claimed more loudly than it is earned. The ledger here is an append-only Merkle-committed chain, not a consensus network: it costs 0.130% of task latency, it lets a party other than the writer re-derive every digest, and it localises tampering to the seam. It does not tolerate Byzantine faults and does not survive a malicious controller, and we say so rather than letting the word imply otherwise.

One component is reported as not-yet-demonstrated rather than as a result. The online weight optimiser runs safely — it can never reach the quarantine gates — but over this run it could not distinguish its own candidate weightings, and the most eye-catching number in its output turned out to be a cold-start artifact. We would rather publish that than a learned-weights improvement the data does not support.

Future work, in the order the evidence argues for it: integrating RAFT so the ledger's replication claim is live rather than standalone; multi-seed live runs so live figures carry intervals; adaptive adversaries that react to their own detection, which is the assumption most likely to be load-bearing; per-client-IP enforcement to close the DDoS response gap; and a longer, harder-loaded run in which the weight optimiser could actually be decided.

The offline scorer replays the recorded evidence through the same classifier implementation the live controller calls, rather than tallying the live label events. Live classification events record label changes only, so counting them would weight a subject that flapped once the same as one that held a verdict all run — and sharing one implementation is what stops the offline number silently disagreeing with the live one.
