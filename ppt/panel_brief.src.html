Zero Trust-Enabled SDN Architecture for Secure and Intelligent Load Balancing in Edge Networks

Complete panel briefing — what it is, what it proves, where it applies, and what to say

In one paragraph. Every load balancer in production today — from a cloud health-check pool to a Kubernetes scheduler to a 5G edge orchestrator — decides where to send work based on what the servers say about themselves. That assumption breaks the moment one of those servers is compromised, rented, misconfigured, or simply selfish. We built an SDN control plane that instead decides from what it observes: it continuously scores every edge server on measured behaviour, and when a server misbehaves it revokes that server in the data plane — as real OpenFlow rules, in under a second — while an append-only cryptographic ledger records why. We then ran the same network, same workload and same six attacks with and without that mechanism, and measured the difference.

1The problem, in plain language

Edge computing pushes computation onto many small, physically exposed, heterogeneously-owned machines: roadside cabinets, factory-floor servers, campus racks, telco base-station sites. Three facts collide there.

1.1 The perimeter model fails at the edge

Classical network security draws a wall and trusts everything inside it. At the edge there is no meaningful inside: a node can be physically opened with a screwdriver, rented to a third party, misconfigured by a subcontractor, or simply be selfish. Classical load balancers — round-robin, least-connections — assume every backend is honest about its state and faithfully performs its work. Neither assumption survives a single compromised node, and neither balancer has any mechanism that could ever notice.

1.2 Self-reported telemetry is the industry norm, and it is trivially gameable

This is the sharp end of the problem and it is worth saying slowly to the panel. Almost every real orchestrator schedules on what nodes claim about themselves: Kubernetes schedules on kubelet-reported resource metrics, cloud auto-scalers on agent-reported utilisation, MEC orchestrators on advertised host capacity. A node that under-reports its load therefore attracts traffic — which is exactly what an attacker wants, whether the goal is to intercept data, degrade the service, or freeload on someone else's SLA.

The attacker does not have to break any cryptography to do this. It just has to lie in a field that everybody believes.

1.3 "Zero Trust" is policy, not implementation, at the network layer

NIST SP 800-207 says never trust, always verify, continuously — but it is an architecture document, not a mechanism. Commercial Zero-Trust products overwhelmingly verify users and client devices at access time. Verifying the serving infrastructure itself, continuously, with consequences in the routing path is much less settled, and that is the gap this project works in.

The honest problem statement — memorise this sentence

“Can an SDN control plane continuously verify edge servers using observed rather than claimed behaviour, and enforce the verdict in the data plane fast enough to matter?”

Our answer, at prototype scale: yes — with isolation inside a 3-second bound — and with the important negative result that score-based trust alone is provably insufficient to do it (§5).

1.4 What we are careful not to claim

  • We do not solve Zero Trust for edge networks in general. We demonstrate one mechanism — behavioural trust plus SDN enforcement — under six modelled attacks.
  • Real adversaries have a larger menu than we cover: collusion between nodes, slow-and-low degradation, adaptive attackers who keep every signal just under threshold, and attacks on the controller itself.
  • The evaluation is emulation (Mininet with real Open vSwitch and real OpenFlow), not a field deployment. The correct phrase is “demonstrated in an emulated network”, never “proven in production”.

2What we built

A trust-aware SDN load balancer for OpenFlow 1.3 networks. The controller computes a per-node trust score from observed behaviour, ranks edge servers by an EdgeScore, installs the routing decision as real flow rules, and quarantines misbehaving nodes in the data plane. Every trust event is recorded in a tamper-evident SHA-256 + Merkle ledger.

2.1 One environment decision to state before you are asked

The original deck specified the Ryu SDN framework. This project runs on os-ken, the actively-maintained fork of Ryu, with the identical API (os_ken.* instead of ryu.*). The reason is environmental and hard: the target OS ships only Python 3.14, there is no Ryu package for it, and Ryu cannot run above Python 3.13. There is no ryu dependency and no ryu-manager anywhere in the repository. Present this as a documented engineering decision, not as Ryu.

The design rule that runs through every layer

The request path writes evidence into TrustState; the 1-second control loop reads decisions out of it. The two never share a code path. That separation is precisely what makes it possible to run the identical trust code in the control arm with enforcement removed — which is what turns our headline comparison into a controlled experiment rather than two different programs.

Why no RDBMS — this is a deliberate answer, not an omission

The ledger is the store of record for trust, and its integrity is cryptographic (hash chain plus Merkle root, verified by GET /ledger/verify and re-verified independently in the browser) rather than referential. The JSONL recording is the durable evidence log that every analysis tool reads back offline. Configuration is YAML. Adding a relational database would add a second, weaker source of truth for data whose integrity requirement is tamper-evidence, not joins.

4How one task flows end to end

{{FIG:fig5_system_workflow.png}}

Phase A — Admission (once per device)

  1. The IoT device asks for a challenge: POST /auth/challenge {device_id}.
  2. The controller returns a fresh 64-bit nonce with a 30-second TTL, single-use.
  3. The device encrypts the nonce under the fleet PRESENT-80 key and returns it to POST /auth/verify.
  4. The controller checks the cryptographic response and the source IP against the provisioned identity roster. Both must pass. A failure returns 403 and publishes an auth_denied event with a structured reason — a refusal that only the refused device knows about is invisible to any later analysis.

Phase B — Routing (once per TCP connection)

  1. The device opens a TCP connection to the virtual IP 10.0.99.254:9000.
  2. The edge switch has no matching flow rule, so it sends a PacketIn to the controller.
  3. edge_selector filters to eligible nodes (trust above the isolation threshold, not quarantined), samples two of them, and scores each by EdgeScore w₁·T + w₂·(1−cpu) + w₃·(1−latency).
  4. The winner is installed as a pair of flow rules that rewrite destination MAC and IP to that specific server — and the reverse rules for the return path.
  5. The dispatch is registered in TrustState, which now holds an outstanding obligation against that server.

Phase C — Execution, verdict and record (once per task)

  1. The server does real bounded work (a hash loop) and answers.
  2. The client reports the outcome — success or timeout, with its own measured latency — to POST /report.
  3. TrustState resolves the dispatch, updates reliability R, latency B and honesty H, and decays the anomaly term A.
  4. In parallel, the 1-second control loop has been polling every server's /status, comparing what it claims against what the controller observed, and raising anomaly signals.
  5. The trust update is batched (10 per block) and committed to the ledger; a block carries a Merkle root over its updates and a SHA-256 hash over its header, chained to its predecessor.

Phase D — Enforcement, when a node fails verification

If trust falls below the isolation threshold, or the anomaly gate fires regardless of trust, the controller: deletes every flow rule carrying that node's cookie with a single cookie-matched OFPFC_DELETE; installs drop rules at PRIO_QUARANTINE_DROP; and re-steers the in-flight dispatches onto surviving nodes. Measured end to end at 25.6 ms mean, 47.3 ms maximum against a 3-second requirement.

Recovery is part of the design, not an afterthought

A quarantined node is not condemned forever. Probation — the half-open leg of a circuit breaker — gives a node that was isolated on the trust rail only, and whose anomaly score has since fallen below the gate, one trial task per interval. Trial flows install above the quarantine drop rules, or they would be black-holed by the very rules they exist to escape. In the run reported in §7 that produced 23 recoveries from 25 quarantines. §14 explains why this mechanism had to be invented.

5The trust model, the anomaly gate, and our strongest finding

{{FIG:fig6_zero_trust_flow.png}}

5.1 The formula

T = α·R̄ + β·B̄ + γ·H̄ − δ·Ā     α=0.35 · β=0.25 · γ=0.25 · δ=0.15
TermNameMeasured from
R̄ReliabilityCompleted versus failed task outcomes, exponentially weighted (λ = 0.85)
B̄Behaviour / latencyObserved response time against the fleet's own median
H̄HonestyDeviation between the load the node claims and the duty cycle the controller derives from completion counts and reported busy time
ĀAnomalyThe detector rail: latency tell, timeout-rate tell, honesty tell, flood tell

Isolation threshold 0.30. Anomaly gate 0.50. Honesty deviation gate 0.40. Poll interval 1 s.

Finding 1 — the published formula provably cannot isolate a competent liar

Replaying the real TrustCalculator against the project's own attack scenarios shows that the original claim “Ā→1 implies T→0” is arithmetically unreachable. Consider a node that lies about its load but still serves tasks correctly. Its reliability is perfect and its behaviour term is near-perfect, so:

T = 0.35(1.0) + 0.25(0.96) + 0.25(0) − 0.15(1.0) = 0.44

δ can only ever subtract 0.15. Dishonesty alone cannot push the score across an isolation threshold of 0.30. A perfectly detected, perfectly dishonest node stays eligible for traffic forever.

Consequence: score-based trust is insufficient for Zero Trust's continuous-verification requirement. An independent anomaly gate (Ā ≥ 0.5 ⇒ quarantine regardless of T) is necessary, not belt-and-braces. This is proven in code by test_f04_non_degrading_liar_needs_anomaly_gate, which drives the real calculator rather than a mock.

5.2 Why this is a contribution rather than a bug report

We kept the published formula byte-for-byte and added a documented gate beside it. The alternative — quietly retuning the weights until the demo worked — would have destroyed the finding and produced a system whose success nobody could explain. A characterised failure mode with a tested fix is the strongest credibility signal available to a project like this.

The live evidence that the two rails are both necessary comes straight out of the recorded run: the sybil and on-off attackers were caught only by the anomaly gate (their trust never fell far enough), while the blackhole attacker was caught only by the trust score and raised almost no anomaly signal at all. Neither rail alone catches all four attackers. That single sentence is the justification for the entire two-rail design.

Finding 2 — a Sybil lie is self-defeating when the telemetry is real

Because our node agents perform real bounded work, a liar that advertises “I am idle” attracts traffic it cannot actually serve, genuinely degrades, times out, and its trust collapses on its own. This emergent self-punishment exists only because the testbed measures real load instead of injecting synthetic telemetry — which most simulation papers in this space do. The pathological remaining case, a liar with enough spare capacity never to degrade, is precisely the case Finding 1's gate covers. The two findings together are a complete story.

5.3 Load balancing: EdgeScore, and why power-of-two-choices

{{FIG:fig7_load_balancing_flow.png}}

The original selector was argmax — take the single best-scoring node. We measured what that does as the fleet grows, driving the real selector inside a queueing model, and found a genuine flaw:

  • With load-only differentiation, argmax spreads traffic fine even at N=64 — it degenerates to join-shortest-queue. So “many servers plus argmax” is not the problem by itself.
  • Once trust is coupled to selection, argmax locks onto roughly two nodes regardless of N — N=8 → 2 used, N=32 → 2 used, N=64 → 3 used. Positive feedback: only completed tasks move trust, so the nodes already winning traffic are the only ones that can build trust. Idle capacity grows linearly with fleet size.
  • Argmax then fails in two different ways at the two ends of offered load: at low load it starves the fleet (Jain fairness 0.176, 13 of 16 nodes idle); at high load almost nothing is starved but throughput saturates around 85 tasks/s from N=8 upward and delivery ratio collapses from 99.2% to 10.5% at N=64.
  • Power-of-two-choices scales linearly: 48 / 95 / 192 / 382 / 762 tasks/s at N=4/8/16/32/64, delivery ratio 99.7–99.8%, delay flat at ~266 ms.

Do not claim p2c as a CPU saving. We measured that too, and it is not one: both strategies cost the same 3/5/9/16/30 µs per decision, because the selector scores and sorts every eligible node either way — the full ranking is returned as the decision's explanation and published to the dashboard. That is a deliberate trade. Claim the p2c win in fairness, throughput and delay; never in CPU.

6.1 Three design decisions worth defending out loud

  1. The flood tell is keyed on the requesting client, never on the edge node it lands on. A server drowning under a flood is not lying about its load — it is telling the truth about being overwhelmed. Blaming the node would repeat a mistake this project has already made twice (§14).
  2. We did not build a literal replay attack. verify_response pops the nonce on first use, so replay was already structurally impossible. Building a fake version of an attack the system already defeats would have been dishonest. The real gap was that the key is fleet-wide, so PRESENT-80 authenticates possession of the key, not the device — which is exactly what source-IP pinning closes.
  3. node_down is deliberately not one of the six attacks. Our blackhole answers /status fine and drops only tasks, so “silent” is a liveness failure, not an attack. Folding it in would inflate the very numbers the classifier exists to measure honestly.

6.2 Naming an attack is harder than detecting it — and we say where the limits are

Two of the six pairs are not separable from a single detection cycle, so the classifier reads an evidence window:

  • Blackhole vs grayhole raise the same signal and differ only in magnitude.
  • Sybil vs on-off raise the same signals and differ only in intermittency.
The tension we measured, and could not tune away

Containment quality and magnitude evidence are in direct opposition. A blackhole fails everything, so it is isolated fastest, so it produces the fewest outcomes with which to characterise it. In one run srv6 produced 3 task outcomes in 312 s; the grayhole, which kept partly working, stayed in circulation and produced 24. The faster the defence, the thinner the evidence for the label.

Our resolution: when no measured rate exists, the trust rail establishes the family and the call degrades to the weaker claim (grayhole), never the stronger one. In every such case the attacker is still caught and still quarantined — only the label degrades. That is the honest framing, and it is the one to use if a panellist asks about the two misclassifications in §7.

Reduction in SLO-violation rate, all at padj = 7.45×10⁻⁹ with rank-biserial r = +1.00 — meaning our system won in 30 of 30 paired seeds. Failure rate falls 97.7% against the strongest baseline and 99.2–99.3% against the trust-blind ones. 14 of 16 comparisons significantly favour the system.

The no_trust column is the one that matters. It is the identical selector with the trust term removed and quarantine disabled — so it attributes the improvement to trust, not to load-aware routing in general.

The two comparisons we lose, and why we report them

Both losses are in the clean scenario, with no attacker present: we are 10.7% worse than round-robin and 4.8% worse than random. That is a genuine cost of a load-reactive strategy and we report it as one. The cause is not the trust term — it is staleness in the load signal that every load-reactive strategy reads. A poll-interval sweep isolates it exactly: halving the poll interval from 1.00 s to 0.50 s closes most of the gap. Being able to name the mechanism behind your own loss is worth more in a viva than not having the loss.

The denominator trap — know this one, it is a classic viva question

An early version of our own harness divided ledger commit cost by the handling time of a single uncommitted request (tens of microseconds) and reported a 0.424 ms commit as 2 155 % overhead. The correct framing amortises the commit over the batch size and divides by end-to-end task latency — the thing the user actually waits for — which gives 0.049 %. If someone challenges the “blockchain overhead” number, this is the reasoning to give.

8.3 Consensus: what RAFT does and does not do here

{{FIG:fig12_raft_failover.png}}

Three real processes over real TCP, under continuous load, with the leader killed by a genuine signal:

  • Leader failover in 0.21 s; 850 of 853 commits succeeded (99.6 %).
  • The outage is three refused attempts — visible only because the client never pauses for the kill.
  • A degraded 2-of-3 cluster costs more per commit (2.23 → 3.08 → 2.58 ms after rejoin). We report the observation; we have not established the cause and do not claim one.
  • A restarted replica rejoins with an empty log and is caught up by the leader — making the crash-fault limitation visible rather than merely documented.
Say this plainly, before you are asked

“RAFT is implemented, unit-proven for safety, and demonstrated live over real TCP with a leader kill. The controller still commits single-replica, and the swap is deliberately deferred.” Every block in every live run carries raft_term = 0 and proposer_id = "controller". Three concrete runtime blockers stand in the way, all identified: nothing drives the election tick inside the controller; commit() would block an OpenFlow handler thread for up to 2 s; and a None return is currently discarded silently, which would lose trust updates on every leadership change. Never let a slide imply the live runs are RAFT-backed.

9Where this is used — real-world application domains

This is the section panellists most often push on, and the trap is breadth. A report that maps its architecture onto one real domain reads as engineering; one that lists eight domains reads as marketing. Lead with MEC, keep industrial IoT as the secondary, and have the rest ready only if asked.

9.1 Strong fit — claim these

① Multi-access Edge Computing (MEC) and the 5G telco edge primary

Telecom operators run third-party workloads on distributed edge sites — thousands of small compute nodes at base stations, central offices and aggregation points. The operator genuinely cannot fully trust every node in that estate: some are in unmanned cabinets, some run tenant software, some are maintained by contractors. And MEC orchestrators route work by self-reported host load today. The mapping onto our architecture is almost one-to-one:

The pitch sentence: “An operator can host a tenant's workload on a node it does not fully control, and still bound its exposure: if the node starts lying or dropping, traffic is revoked from it in under a second and there is a signed record of why.”

② Industrial IoT and the factory / OT edge secondary

Operational-technology networks increasingly use SDN-style central control. The scenario that keeps OT engineers awake is not a machine that stops — that is obvious and alarms fire — it is a controller that keeps “working” while lying about its state, because every safety and scheduling decision downstream is computed from that state. Our anomaly gate is aimed at exactly that case: quarantine on behaviour, not merely on a score. And the sub-3-second bounded isolation is the kind of number OT people ask for first, because it maps onto a process safety time.

③ Smart campus and smart-city gateways

Many small operators, physically accessible cabinets on poles and in kerbside enclosures, and no dedicated security operations centre watching them. The value here is unstaffed autonomous operation: a control plane that detects, contains and re-steers by itself at three in the morning, and leaves an audit trail a municipal operator can hand to an auditor afterwards. This is the single clearest “nobody is watching” story in the list.

10.1 What a real deployment would require

If a panellist asks “could you actually deploy this tomorrow?”, the honest answer is “not tomorrow, and here is exactly what stands between”:

  1. An OpenFlow 1.3-capable or otherwise programmable data plane (P4, eBPF/XDP, or a smart NIC). The enforcement mechanism is what makes the verdict binding; without it the trust score is advisory only.
  2. Per-device identity provisioning — our source-IP pin is derived from a provisioned roster. Real deployments would want per-device keys and a 128-bit primitive behind the same Authenticator seam (§13).
  3. Controller redundancy. The controller is currently a trusted single point. Wiring in the RAFT cluster we already built is the first step; full controller distribution is future work.
  4. Multi-host validation. Everything measured here runs on one machine — real processes and real sockets, but not real network separation.

11.3 Why the ledger is not decoration

This is worth rehearsing because “blockchain” invites cynicism, and the cynicism is usually earned. Our defensible position, stated in one paragraph:

The ledger provides tamper-evidence — hash-chained, Merkle-proven history, so retroactive falsification of trust records is detectable and localisable to the seam — and availability through replication, within a controller cluster that is itself inside the trusted computing base. It is not a permissionless blockchain, it does not tolerate Byzantine replicas, and it does not need to: our threat model puts malicious behaviour at the edge nodes, not inside the controller cluster.

And when the inevitable follow-up comes — “then why not just use a signed append-only log?” — the honest answer is: a hash-chained Merkle log replicated by RAFT essentially is one, structured for per-record proofs and batch commits. “Private blockchain” is the deck's name for it. Conceding that gracefully costs nothing; defending the buzzword costs credibility.

12What is genuinely novel here

Three findings, none of which came from the literature review. All three came from building the thing and measuring it.

Finding 1 — the published trust formula cannot isolate a competent liar

Covered in full in §5. The short version: a node that lies about its load while serving correctly floors at T = 0.44 against an isolation threshold of 0.30, so a perfectly-detected liar remains eligible for traffic forever. δ can subtract at most 0.15. The consequence is that an independent anomaly gate is necessary, not optional — and the live run confirms it, with two attackers caught only by the gate and one caught only by the score.

Why it is a contribution: we found the published formula insufficient, characterised exactly why, kept the formula intact, and added a documented gate. Quietly patching the weights would have destroyed the result.

Finding 2 — a Sybil lie is self-defeating when telemetry is real

Because the node agents perform real bounded work, a liar advertising “I am idle” attracts traffic it cannot serve, degrades, times out, and its trust collapses on its own. This emergent self-punishment cannot be produced by injected telemetry — and injected telemetry is what most simulation papers in this space use. The remaining pathological case (a liar with spare capacity that never degrades) is precisely the case Finding 1's gate covers.

Finding 3 — honest packet visualisation in SDN is structurally hard

Once a flow rule is installed, matching packets are forwarded entirely in the data plane and never reach the controller again. A controller therefore cannot honestly animate per-packet flow from PacketIn events. Our dashboard drives its animation from 1 Hz OFPFlowStatsRequest counter deltas and prints the measured packets-per-second on screen so the claim is checkable. It is a small but real observation about SDN observability — and it is the confident answer to “why doesn't your dashboard show every packet?”

Supporting contributions

  • Trust decisions enforced in the data plane — VIP rewrite plus cookie-scoped rule deletion on trust collapse, inside a bounded isolation NFR — rather than simulated in a scheduler.
  • “Unreachable equals anomalous” — an unresponsive status endpoint is itself an anomaly signal. This started as a bug caught by writing tests and became a design rule, with a companion rule that a node which has never been seen is UNKNOWN, not anomalous.
  • A control arm, not a claim. Building a complete no-zero-trust version of the same system, launched by the same code, is what makes §7 an experiment. Most projects at this level compare against a description of a baseline rather than a running one.
  • Running a full SDN research stack on Python 3.14 / os-ken with a hand-written application manager, where the standard tooling does not exist.

Every live-run defect in this project was the controller's own bookkeeping feeding a working detector bad input. Not once were the detectors at fault. That distinction — “correctly flagged” versus “unable to be un-flagged”, “correctly isolated attacker” versus “wrongly starved honest node” — is the discipline that got the project from a total collapse to a perfect honest side in ten runs.

16Anticipated panel questions and answers

Rehearse these. The first eight are near-certain.

Your title says Zero Trust, but your controller is fully trusted. Isn't that a contradiction?
Yes, and we state it as a limitation rather than hiding it. It is the standard SDN trust model: the control plane is inside the trusted computing base. Our Zero Trust claim is scoped to the serving infrastructure — the edge nodes are never trusted, are verified continuously, and are verified on observed rather than claimed behaviour. Replicating ledger state with RAFT is a first step toward controller redundancy; full controller distribution is named future work.
RAFT is crash-fault tolerant, not Byzantine. A malicious replica can lie and RAFT will happily replicate it. So what does your blockchain actually secure?
Two things, precisely: tamper-evidence — the hash chain and Merkle roots make retroactive falsification detectable and localisable to the seam — and availability under replica crashes. Both hold within a controller cluster that is itself in the trusted computing base. It is not permissionless, it does not tolerate Byzantine replicas, and it does not need to, because our threat model puts malicious behaviour at the edge nodes. If you follow up with “then why not a signed append-only log?” — a hash-chained Merkle log replicated by RAFT essentially is one, structured for per-record proofs and batch commits.
PRESENT-80 is an 80-bit cipher. That is below modern security margins.
Correct, and we frame it accordingly: an ISO/IEC 29192-2 lightweight block cipher appropriate to severely constrained IoT devices, used here to demonstrate the challenge–response architecture. A production deployment would drop a 128-bit primitive behind the same Authenticator seam — and that seam already exists, which is why this is a swap and not a rewrite. Separately, the more interesting weakness is not the key length at all: the key is fleet-wide, so it authenticates possession of the key rather than the device. That is the gap source-IP pinning closes.
Two of your eight attacks were misclassified. Isn't that a failure?
Both misses are in the right family, so the response would have been identical either way — the attacker was still detected, still quarantined, still contained in single-digit seconds. And the cause is a limit we characterised in advance: containment quality and magnitude evidence are in direct tension. The faster you isolate an attacker, the less evidence exists to say how much it was dropping. In that run our defence was faster and cleaner than ever — which is precisely what starved the classifier. We traded two label-precision points for a perfect honest side: zero honest mislabels, zero honest quarantines, zero route denials.
Two servers got no traffic at all. Isn't that a load-balancing flaw?
There are two distinct zero-traffic cases and they must not be conflated. A malicious node receiving zero traffic is the isolation working correctly. A healthy node receiving zero traffic is a genuine flaw — starvation — and we found it, characterised its root cause (argmax plus trust-coupled selection produces rich-get-richer lock-in onto ~2 nodes regardless of fleet size), and fixed it with power-of-two-choices plus ε-exploration. Note also that starved healthy servers receive zero packets — they do not drop anything. Only a quarantined node gets drop rules.
Your system is slower than round-robin when there is no attacker. Doesn't that undermine the whole thing?
It is, by 10.7% on SLO violations in the clean scenario, and we report it. The cause is not the trust term — it is staleness in the load signal that every load-reactive strategy reads, including least-connections, which does far worse. We isolated it with a poll-interval sweep: halving the poll interval closes most of the gap. The trade is explicit: in a clean network you pay a small cost; under any of the four attack scenarios you win by 15–69%.
Why doesn't your dashboard show every packet?
Because it structurally cannot, and animating one would be a lie. Once a flow rule is installed, matching packets are forwarded entirely in the data plane and never reach the controller again. We therefore drive the animation from 1 Hz flow-statistics counter deltas and print the measured packets-per-second on screen so the claim is checkable. This is Finding 3 — a real observation about SDN observability.
How do you know your results aren't just the trust mechanism getting lucky on one run?
Three independent lines of evidence. First, a controlled comparison: same topology, same devices, same attacks on the same schedule, same launching code, differing only in whether anything acts on trust. Second, a 600-run seeded statistical harness driving the real selector and the real calculator — 14 of 16 comparisons favour the system at padj = 7.45×10⁻⁹ with the system winning 30 of 30 paired seeds. Third, an ablation: the same selector with only the trust term removed, which is what attributes the gain to trust rather than to load-aware routing generally. And we state the limitation plainly — every live figure is a single seed.
What happens if a quarantined node was innocent?
It gets out. Probation is the half-open leg of a circuit breaker: a node isolated on the trust rail only, whose anomaly score has since fallen below the gate, receives one trial task per interval, and the trial flow installs above the quarantine drop rules so it is not black-holed by the rules it exists to escape. In our best run that produced 23 recoveries from 25 quarantines. We had to invent this because in an early run quarantine was an absorbing state — isolation starved the very evidence needed to leave it.
Why os-ken and not Ryu, as your deck specified?
The target OS ships Python 3.14; Ryu cannot run above 3.13 and has no package for it. os-ken is the actively-maintained fork of Ryu with an identical API. It is an environment-driven engineering decision, documented, with no ryu dependency anywhere in the repository.
Would this work at 1 000 nodes?
We do not know, and we will not claim it. What we measured: at 8 servers we measure live; beyond that we simulate the fleet while executing the real selector, up to N=64. That supports the claim that the selection rule, not the hardware, is what stops scaling under argmax — power-of-two-choices scales linearly where argmax saturates. It does not support a capacity figure for real machines. Running N=64 on a 4-core box would measure the laptop, not the architecture.
Where would this actually be deployed?
MEC and the 5G telco edge first — the mapping is nearly one-to-one: our controller is the orchestrator, our edge servers are MEC hosts, our IoT clients are user equipment, and MEC orchestrators route on self-reported host load today. Industrial and municipal edge second. Explicitly not the public cloud, where the operator owns and attests its own hardware, and not consumer IoT, which would be buzzword marketing.
Isn't this just a health check with extra steps?
A health check asks the backend a question and believes the answer, and its verdict is binary. Ours computes a graded score from evidence the backend cannot fabricate — completed versus failed outcomes, observed response time against the fleet median, and the gap between claimed load and a duty cycle the controller derives itself — and adds a second, independent gate that can act when the score arithmetically cannot. The case that separates them is our central one: a host returning perfect responses while lying about capacity passes every health check ever written.
Your attacker share is still 12.5%. Why not zero?
Because attackers are behaviourally identical to honest nodes before onset — every attack in our configuration has a delayed onset precisely so that the detectors must notice a change rather than recognise a permanently odd node. The 12.5% is overwhelmingly pre-onset traffic plus the seconds before containment. The baseline's 30.5% is the same traffic plus everything that continued flowing for the rest of the run because nothing could stop it.
What is the single biggest weakness of this project?
That every live figure comes from a single run at a single seed. We have statistical rigour on the simulation harness and fidelity on the live runs, but not both on the same measurement. That is the honest answer, and it is the first thing we would fix with more time — ahead of wiring in RAFT and ahead of DDoS throttling.
What did you personally learn from building this?
That the hard part was never the detectors. Every single defect across eleven live runs was the controller's own bookkeeping feeding a working detector bad input — a stale counter, a rejuvenated timestamp, a task charged to the wrong node. The discipline that got us out was refusing to conflate two things that look alike in an average: “correctly isolated attacker” versus “wrongly starved honest node”, and “correctly flagged” versus “unable to be un-flagged”. Every metric in this project that touches quarantine reports those separately.

17.1 The demonstration, in order

  1. Live Mininet run — sudo python3 run_demo.py --mode mininet --config config/params_trust_full.yaml
  2. The dashboard at http://localhost:8081/ — quarantine, re-steer and block commits are visible as they happen. Point at the trust curves diverging when each attack arms.
  3. Real flow tables — mininet> dpctl dump-flows -O OpenFlow13 | grep cookie=0x5a. This is the proof that the decision is enforced in the data plane and not simulated.
  4. The API by cURL — iot1 curl -s http://10.0.99.254:8081/node/status
  5. The ledger tamper control — break the chain in the browser and watch the break localise to the seam. The page recomputes SHA-256 itself rather than trusting the controller's own valid flag.
  6. Recorded RAFT failover — python3 -m blockchain.raft_timeline --duration-s 45 --kill-at-s 15 --restart-at-s 30
  7. The test suite — python3 -m pytest -q, 50.7 s, 993 passing.

17.2 Environment prerequisites — check every one before the room

  1. sudo service openvswitch-switch start — WSL does not auto-start it, and without it the topology hangs with no visible error.
  2. sudo modprobe -a sch_htb sch_netem sch_tbf sch_prio ifb — note the -a; without it only the first module loads and the rest are treated as parameters.
  3. sudo mn -c between runs, to clear stale veth state.
  4. Controller first, topology second. A switch that connects to nothing installs no rules, and every connectivity test silently times out — which looks exactly like a freeze.
  5. Live mode runs under sudo, so outputs land owned by root. The next non-sudo controller then dies with a permission error that reads like a broken controller. The runner chowns artefacts back at the end of a run; older ones need sudo chown -R $USER data logs.
Fallbacks, in order of preference

1. Replay a recorded run into the live dashboard — python3 -m dashboard.replay data/events.jsonl --loop, then open localhost:8082. It exercises every panel with real recorded events and needs no sudo and no Mininet.
2. Run the four offline scorers against an archived recording — NFR report, confusion matrix, availability report, interval report. None needs the controller stack installed.
3. Run the 600-run statistical harness — it takes about 40 seconds and needs nothing but Python.
4. The figures in this document and the generated slide figures under ppt/figures/.

Archive the recording before any new run. Live mode unlinks data/events.jsonl at startup and data/ is gitignored — copy it to data/events_runN.jsonl the moment a run finishes, or its numbers cannot be re-derived.

18Glossary and provenance

18.1 Terms a panellist may ask you to define

SDN — Software-Defined Networking: the forwarding decisions are made by a central controller, and switches only execute installed rules.

OpenFlow 1.3 — the protocol between controller and switch. Rules match on packet fields and carry actions, priorities and cookies.

Flow rule / cookie — an installed match-action entry. A cookie is an identifier we attach so all of a node's rules can be deleted in one operation.

VIP — Virtual IP. Clients connect to one address; the controller rewrites the destination, so the client never learns and never chooses which server serves it.

PacketIn — what a switch sends the controller when no rule matches. This is where a routing decision is made.

EMA (λ = 0.85) — exponential moving average; recent evidence dominates, older evidence decays smoothly.

Jain fairness index — 1.0 means perfectly equal shares; lower means more skew. Must be read over a stated population (§7.3).

Merkle root — one hash summarising a set of records, allowing any single record to be proven a member without revealing the rest.

Tamper-evident — modification is detectable, not prevented. This is the correct word for our ledger.

Crash-fault vs Byzantine — crash-fault tolerance survives replicas that stop; Byzantine tolerance survives replicas that lie. Ours is crash-fault.

PRESENT-80 — an ISO/IEC 29192-2 lightweight block cipher for constrained devices, 80-bit key.

TOFU — trust on first use: the first host to claim an identity owns it. Our fallback where no provisioned roster entry exists.

Power-of-two-choices — sample two candidates at random, take the better. Provably far better tail behaviour than picking the single best from a stale view.

Wilcoxon signed-rank / Holm–Bonferroni — a paired non-parametric test, and the correction applied because testing against four baselines four times inflates the false-positive rate from 5% to ~19%.
