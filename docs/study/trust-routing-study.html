Rec 01

Zero-Trust SDN · Controller telemetry study

Trust-weighted routing concentrates load, and cannot tell "untested" from "untrusted"

An empirical read of 28,338 live routing decisions on a Mininet testbed. The trust term that protects the fleet from a dishonest node also, by the same mechanism, locks out a healthy one — and over a longer horizon it keeps changing which one.

Runs 498 s + 2,832 s Decisions 28,338 Outcomes 28,335 Fleet 4 edge nodes · 12 IoT clients Controller os-ken / OpenFlow 1.3

Figures generated from the controller event bus (data/events.jsonl). Sections 1–4 and the appendix describe run A, one continuous 498 s run; Sections 6–8 describe run B, 2,832 s on the same topology; Section 5 references an earlier 24-minute run. Each is labelled where it appears.

Summary of findings

F1

Half the fleet never received a single task

Two of four nodes served all 3,742 requests. The other two — one healthy, one hostile — were selected zero times. Capacity utilisation was 50% while every served task succeeded.

F2

The trust signal is self-reinforcing

Trust is earned only by completing tasks, and tasks are awarded by a score that weights trust most heavily. A node that starts fractionally behind does not catch up. srv2 — healthy, fast, honest — sat frozen at its initial 0.500 for all of the 498 s run, and for 19,320 consecutive decisions of the longer one.

F3

Scoring and quarantine defend against opposite attacks

The score starves an attacker that looks bad; quarantine catches one that looks good. The sybil node was neutralised by the former and never triggered the latter — it was avoided, not detected.

F4

Three defects were measurement artefacts, not logic errors

Every false quarantine observed during development traced to comparing two quantities sampled on different time bases. The detector was sound; its inputs were not commensurable.

F5

Over 47 minutes, the starvation rotates

srv2's exclusion broke after 2,239 s — on one chance win during a load spike, which a λ=0.85 EMA converted into a 0.22 trust jump. srv1 then took its place and was idle for the final 194 s. Utilisation stays at 50%; only the identity of the idle half changes.

F6

Success becomes trust-negative above 13% occupancy

The resource-honesty term compares an instantaneous self-report against a 3-second windowed estimate. The gap grows with load, so a busy honest node loses trust for completing tasks — the feedback that unseats each leader in turn.

F7

The weight optimiser has nothing to learn

UCB1 picked all five arms 49–55 times out of 263: their mean rewards span 0.004 against within-arm noise of 0.011–0.015. With every arm at 100% task success, the reward measures the workload rather than the policy.

§ 1

Section one

Method

The system under study is a trust-aware SDN load balancer. Twelve emulated IoT clients issue tasks to a virtual service address; an OpenFlow controller intercepts each new connection, selects an edge node, and installs a rewrite rule pair steering that flow to the chosen server. Selection maximises a weighted score:

EdgeScore(n) = w₁·trust(n) + w₂·(1 − cpu(n)) + w₃·(1 − latency(n)), with weights tuned online by a UCB1 bandit over five fixed arms.

Trust is updated only on a completed task outcome. Nodes report CPU load over a health endpoint; the controller measures that endpoint's round-trip itself rather than trusting the node's self-reported figure.

One node, srv3, runs a sybil attack: it reports a fixed cpu_load = 0.10 while burning four background CPU threads. One client, iot12, holds a deliberately wrong PRESENT-80 key. The remaining three nodes and eleven clients are honest.

All figures below are drawn from the controller's own event stream — routing decisions, per-second node snapshots, and switch flow counters — for one continuous 498-second run. Section 5 additionally references an earlier 24-minute run, and is labelled where it does.

§ 2

Finding one

Load concentrates on half the fleet

Across every one of 3,742 routing decisions, the controller chose srv4 or srv1. It never once chose srv2 or srv3.

The distinction matters. A node that ranks last is being correctly avoided; a node that ranks second and never wins is being starved. Figure 2 separates the two cases, and the next section explains why the second one is stable rather than transient.

§ 3

Finding two · principal result

Trust compounds, so an early gap does not close on its own

Trust changes only when a task completes. A node that is not selected therefore holds its score indefinitely — not decaying, not recovering, simply frozen at whatever it last was.

This is a preferential-attachment loop. Selection grants the only evidence that improves the score that governs selection, so a marginal early lead compounds into a permanent one. Three consequences follow.

  • Half the fleet's capacity is unavailable while the system reports every node healthy and every task successful. Nothing in the telemetry flags a problem.
  • The score cannot represent uncertainty. A node that has never been tried and a node that has been tried and found mediocre both sit at 0.500. The system has no way to express "unknown" as distinct from "average".
  • Starvation is indistinguishable from correct avoidance. srv3 is avoided because it is genuinely slow; srv2 is avoided for no reason at all. Both appear in the telemetry as a node with 0.500 trust receiving no traffic.

The standard remedy is to make the selector occasionally sample nodes it does not favour, which is precisely the explore/exploit trade-off the project already solves with UCB1 — but applies to weight tuning rather than to node selection. The bandit optimises how to rank; it does not ensure the ranking is informed. (Section 8 shows it is not learning much about ranking either.)

One caveat, established in Section 6 and worth carrying forward from here: over a run eight times longer than this one, the gap does eventually close — not because the score corrects itself, but because a load spike on the leaders lets the starved node win a single task by chance. "Does not close on its own" is the accurate claim. "Never closes" is what 498 seconds of evidence looks like.

§ 4

Finding three

Two defences, aimed in opposite directions

The controller can exclude a node two ways: the score can rank it out of contention, or the anomaly gate can quarantine it outright. Which one engages depends on whether the attack makes the node look attractive or unattractive.

That measured latency feeds the score's third term, so the sybil sinks to last place and is starved of traffic. The attack fails — but it fails silently. Trust never collapses, because trust requires completed tasks, and it is given none. It ends the run at 0.500, indistinguishable from a node nobody happened to pick.

The reverse case is the packet-drop attack, which the same codebase supports. A dropping node accepts connections and never answers, so it reports genuinely idle CPU and answers its health probe fast — the most attractive profile on the board. It attracts maximum traffic, every task times out, and the timeout tell trips the anomaly gate within four outcomes. It cannot starve itself, because looking good is the whole attack.

The project's own threshold contract anticipates exactly this asymmetry: the anomaly gate exists because the trust formula "cannot isolate a node that lies about its load but still serves tasks well" — it floors around 0.44, never crossing the 0.3 isolation line. Scoring handles what it can see as bad; quarantine is the backstop for what looks good and behaves badly.

The releases matter as much as the detections. Quarantine installs data-plane drop rules; if those rules also blocked the health probe, the signal that clears a node would be the signal quarantine suppresses, and every quarantine would be permanent. The 1.1-second round trips in Figure 6 are that recovery path working — nine raised, nine cleared, none stuck.

§ 5

Finding four · methodology

Sampling two quantities on different time bases

Reaching the run above required fixing three defects that presented as false quarantines. All three shared one root cause, and it is a measurement problem rather than a logic one. This section draws on an earlier 24-minute run.

The honesty check asks whether a node's claimed CPU matches the load the controller believes it has placed there. Both sides of that comparison were being sampled incorrectly.

The controller's side

Observed load was computed as inflight / concurrency read at the polling instant. With concurrency 4 that is a step function over {0, 0.25, 0.50, …}. A node serving two concurrent requests at the sampled millisecond reads 0.50; against a truthful claim of 0.00 that is a 0.50 deviation, past the 0.40 threshold on its own. A healthy node was quarantined for it:

The node's side

Averaging only the controller's half made it worse in the opposite direction. The agent samples active / concurrency the moment its handler runs, so its claim is a step function too. Once the controller's side was a 3-second integral and the node's side was still an instant, the check began firing the other way — a node caught mid-burst reporting 0.50 against a windowed 0.03.

Replaying all 1,320 recorded honesty trips from that run, averaging the node's claim over the same window avoids exactly three. Those three are the trips that started each cascade. The remaining 1,189 are downstream of the third defect.

The lock

The sweep that reclaims abandoned dispatches ran only when a new dispatch was registered. Once every node was quarantined, nothing registered — so the sweep stopped exactly when it was needed. Whatever was in flight at that moment stayed in flight: inflight froze at 3 for eight minutes, holding observed load at 0.75 against a truthful 0.00 and re-tripping the check every second. A transient false positive became terminal.

The general lesson is worth stating plainly, because it is not specific to this system: a detector that compares two measurements is only as sound as their commensurability. Each quantity here was individually correct. The defect was that one was an instantaneous sample and the other a time integral, and nothing in the type system or the tests said they could not be subtracted.

§ 6

Finding five · longer horizon

The lock is not permanent. It rotates.

Section 3 concluded that an early gap never closes. That conclusion was drawn from 498 seconds, and it is wrong — but only about the timescale. This section uses a second, longer run: 2,832 s (47 minutes), 24,596 decisions, same topology, same four nodes, same attacker.

For the first 2,239 seconds the longer run reproduces the short one exactly: srv1 and srv4 split the traffic, srv3 is starved as the sybil, and srv2 — healthy — receives nothing across 19,320 consecutive decisions. Then, at t = 2,238.8 s, srv2 wins one.

Two things break at once, and they are the same mechanism with the sign flipped.

  • Entry is won by noise, not by merit. At t = 2,238.8 s both leaders were mid-burst — srv1 and srv4 were carrying queue occupancy around 0.18–0.23 and answering in 110–150 ms — and the ranking momentarily read srv2 0.587, srv1 0.546, srv4 0.498. srv2 won one task on a transient. It succeeded in 134 ms, and λ = 0.85 converted that single success into a 0.22 trust jump. The exclusion was undone in one sample by exactly the compounding that created it.
  • Exit is caused by winning. srv1 lost its place while serving successfully — 11,584 tasks, zero failures. Section 7 shows what took it down.

So the correct statement of Finding 2 is narrower and worse. The system does not permanently exclude one node; it permanently excludes some node, and which one is decided by noise. Over 498 s that looks like a stuck node. Over 2,832 s it is a slow rotation with hysteresis, in which capacity utilisation stays near 50% while the identity of the idle half drifts.

§ 7

Finding six · mechanism

The honesty term taxes a node for being busy

Trust is not only reputation. The formula is T = α·R̄ + β·B̄ + γ·H̄ − δ·Ā with α=0.35, β=0.25, γ=0.25, δ=0.15, and the H term scores resource honesty: how closely a node's self-reported CPU matches the load the controller believes it placed there. It is the anti-sybil term, and on a busy honest node it misfires.

The node reports active / concurrency sampled the instant its /status handler runs. The controller compares that against occupancy integrated over a 3-second window. Section 5 fixed the instantaneous/integrated mismatch on the controller's side of one comparison; this is the same mismatch surviving in another, and it no longer trips the quarantine gate — it just quietly subtracts trust, in proportion to load.

This closes the loop that Section 6 opened. Selection raises a node's occupancy; occupancy above ~0.13 makes each further success trust-negative; falling trust eventually surrenders the top rank to whichever node has been idle — and an idle node has occupancy near zero, so it earns at the full +0.030 while it holds the lead. The system oscillates because success is penalised at exactly the load that success produces.

srv1's collapse is this in miniature. Its final two reports before freezing were successes at 105 ms and 135 ms with observed occupancy 0.232 against a claimed 0.00 — a 0.232 deviation, well under the 0.40 quarantine threshold, and quite enough to take 0.14 off its trust in two samples.

The deviation never reaches the anomaly gate, so nothing is ever flagged. This is the failure mode Section 5 warned about, in its quiet form: the earlier defects were loud because they crossed a threshold and quarantined a healthy node. This one crosses no threshold at all. It just makes the busiest honest node look marginally dishonest, forever, and the only symptom is that the fleet keeps changing its mind about who is trustworthy.

§ 8

Finding seven

The weight optimiser cannot learn, because its reward is saturated

The three EdgeScore weights are tuned online by a UCB1 bandit over five fixed arms, re-evaluated roughly every ten seconds against a reward built from the outcomes in that window. Over the 47-minute run it made 263 arm selections.

UCB1 is behaving correctly. Its exploration bonus keeps pulling under-sampled arms because the observed means never separate far enough to justify committing, and they never separate because the reward is dominated by task success rate — which was 100% under every weighting, on a fleet where two nodes are always fast and one is always avoided. There is no weight vector in the arm set that makes this workload fail, so there is nothing to learn.

The practical consequence is not that the optimiser is harmful; it is that the weights are effectively being randomised every ten seconds, and the study's other findings hold across that randomisation. The starvation in Section 6 persisted for 37 minutes while the trust weight w₁ was being cycled between 0.34 and 0.70. That is worth knowing: it means starvation is not an artefact of one unlucky weight setting.

A reward that every arm can saturate measures the workload, not the policy. Reporting mean reward 0.93 reads as "the optimiser is doing well" when the honest summary is "no arm was ever tested against a condition it could fail". The condition features already recorded alongside each decision — mean trust, mean load, quarantine count — are the raw material for a reward that could discriminate; none of them currently enters it.

§ 9

Section nine

Discussion

Read together, the findings describe a system whose defensive properties are stronger than its distributive ones.

On defence the result is genuinely good. Across 3,742 decisions the dishonest node received no client traffic at all, and the unauthorised client was refused admission in 77 ms by the PRESENT-80 handshake, before any routing logic saw it. No task was ever served by a node that would have mishandled it. That the sybil was never formally quarantined is, arguably, the stronger claim: the defence held without needing to detect the attack, because the score is computed from a quantity the attacker does not control.

On distribution the same mechanism misfires. Trust-weighting assumes the score reflects a node's quality, but for an unsampled node it reflects only its history of not being sampled. The system conflates two very different statements — "this node performs at 0.5" and "this node has never been asked" — and the consequence is that half a healthy fleet sat idle while the telemetry reported everything nominal.

The longer run sharpens that into something less like a bug and more like a property. Sections 6 and 7 show a closed loop: winning traffic raises occupancy, occupancy above ~0.13 makes each further success cost trust, and the lead eventually transfers to whichever node has been idle long enough to look clean. Utilisation stays near 50% throughout; only the identity of the idle half changes, and it changes on noise rather than on evidence. A short observation window reads this as a stuck node, a long one as a slow oscillation, and neither reading shows up as an incident.

Whether that trade is acceptable depends on the deployment. Where capacity is plentiful and hostility likely, starving anything suspicious is the right default. Where capacity is scarce, idling 50% of it because of early noise is a serious cost — and one that would not appear in any dashboard the system currently produces, because every node is healthy, every task succeeds, and the optimiser reports a reward of 0.93.

§ 10

Section ten

Limitations

  • Two runs, one topology. Findings come from a 498-second run and a 2,832-second run on the same 4-node fleet. Two runs establish that the starvation is not a one-off and that it eventually breaks; they do not establish a distribution for when it breaks. The single observed rotation took 37 minutes, and one observation of a stochastic event is not an estimate of its period.
  • Which node starves is not predicted. srv2 was the excluded node in both runs, and srv1 became the second excluded node late in the longer run. Whether that ordering reflects anything structural — link placement, agent start order — or is purely the early coin-flip this study claims it is, would need runs with the node roles permuted.
  • Offered load is low. At roughly 8.7 tasks per second across four nodes, queue occupancy stays under 0.4. The CPU-honesty check depends on occupancy being informative, and at this load it is only marginally so — which is why the sybil's queue-based tell never fires and its latency tell does all the work. It also means the honesty tax in Section 7 is measured over a narrow occupancy range and extrapolates poorly.
  • One attack of each kind. The drop-attack analysis in Section 4 is derived from the agent implementation and threshold contract, not observed in this run — no node was configured to drop during it.
  • Emulated timing. Mininet link delays are synthetic and the controller shares a host with the data plane, so absolute latencies are not meaningful. Only the separation between nodes is, and that is what the argument rests on.
  • The observer is the system. All measurements come from the controller's own event bus. Section 5 is a direct demonstration that this instrument can be wrong, and Section 7 argues that a related mismatch is still live. The figures here postdate the Section 5 fixes but are not independently corroborated.
  • The optimiser confounds everything. Weights were being cycled every ten seconds throughout both runs (Section 8), so no figure in this study describes a fixed scoring function. That the findings survive the cycling is evidence of robustness, but a controlled comparison would need the optimiser pinned to one arm.
§ 11

Section eleven · added after the two runs above

The fix: power-of-two-choices

The starvation is the textbook failure of argmax selection — one winner per decision, so a node a hair behind never wins and, once trust entrenches a pair, the rest starve. The standard remedy (Mitzenmacher, The Power of Two Choices in Randomized Load Balancing, IEEE TPDS 2001) is to stop taking the single best: sample two eligible nodes at random and route to the better of the two. Quarantine still runs first, so the sybil is still excluded — only the choice among the healthy nodes changes.

The panel below is a controller-in-the-loop simulation over the real selector (controller/edge_selector.py) — four identical, healthy, honest nodes, the same 0.50/0.30/0.20 weights and 1 s poll as the runs above, no attacker. It is not a third Mininet run; it isolates the selection rule. Under argmax two nodes take everything, exactly as in Runs A and B; under power-of-two-choices all four share the load.
